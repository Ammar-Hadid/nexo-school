## D02 local implementation boundary

D02 is dependency-ready after this baseline/decision mapping. The approved architecture already selects self-hosted Better Auth, Prisma/PostgreSQL, invite-only adults and guardian MFA; no new service or public signup decision is needed. See [ADR-003](../architecture/decisions.md#adr-003--guardian-approved-enrollment-independent-passkey-login) and [identity architecture](../architecture/initial-architecture.md#enrollment-independent-login-revocation-and-recovery).

Use a disposable local PostgreSQL database and synthetic identities. Implement a bounded, operator-invoked adult bootstrap, with no web signup path and no automatic startup seeding. Validate local target/origin configuration before mutation. Use supported library account/password/MFA/recovery facilities; do not copy the spike's disposable factor-reset shortcut into the application. Synthetic email verification may use a local test delivery adapter, clearly identified as test delivery; production verification requires its own configured delivery path.

The bootstrap must fail closed on repeat/concurrent creation and partial failure, avoid printing credentials or recovery secrets, and never grant a student adult authority. Adult recovery must preserve the approved MFA boundary, revoke affected sessions and record the recovery without secret values. D02 must verify the supported library behavior and record the exact bootstrap/recovery mechanism before calling its acceptance complete; unsupported safe recovery is a D02 blocker, not permission for a password-only downgrade.

Keep configuration and runtime auth adapters server-only. Do not expose a catch-all endpoint until every enabled route is intentionally allowed and tested. D03 adds family ownership; D04 adds supervised student/browser passkeys. D02 does not claim either is delivered by installing auth tables.

Required D02 evidence: clean local migration and repeat setup, bootstrap race/replay/rollback cases, public signup and unauthorized bootstrap denial, session/MFA/recovery failure cases, server/client secret boundaries, and root checks appropriate to the implementation. No remote database, paid provider, real learner data, production email or deployment is authorized.

## Version and publication contract

- A rubric version freezes its criteria, response policy and named evaluator version. Naming an evaluator does not implement it.
- A content version freezes its prompt, response/evaluation specifications, explanation, rights declaration and provenance. Its fingerprint also includes stable content identity/revision, coverage ID/hash and rubric ID/hash. Response/evaluation specifications are data, never executable code.
- Canonical JSON orders object keys, preserves arrays/text and rejects non-JSON values. SHA-256 covers the full version envelope. PostgreSQL also verifies snapshot hashes, identity fields and restrictive version references.
- Every stored revision is immutable, including drafts. An edit creates a new positive revision under the same content/rubric identity; reusing a revision with changed bytes returns conflict. Exact retries reuse the existing record.
- A review is an explicit authenticated human-content-review action for one exact content hash, including the pinned rubric. Approved and rejected decisions are terminal for that revision. A correction/reconsideration creates a fresh revision and requires a fresh review. Automated/model-supplied authority and reviewer IDs are not accepted.
- Missing content/rubric/coverage, empty/incomplete envelopes, absent review, rejected review and mismatched hashes cannot publish. Database foreign keys tie a publication to the approved review of that same version/hash; immutable triggers block later mutation/deletion. Publication and its audit commit together, and exact concurrent retries create one publication.
- Content publication is **local-synthetic-practice only** at both the application and database boundary. It supplies no mastery/skip permission. No new content is wired into assignment, grading or evidence adapters. The old D05 synthetic seed remains the current saved-task source.

Structural validation proves record shape and reference integrity, not Dutch semantic quality, correct keys, pedagogical bounds or family independence. Actual human content review must examine the full prompt, key, explanation, rights and linked rubric. Simulated review actions in tests are not actual human approval. Template certification/automatic numerical publication is D11; semantic review UI is D14; withdrawal/correction is D15; production subject adapters and educational evidence remain their later tasks. This implementation deliberately provides no bypass or automatic-publish lane.

## Authority and use

`src/server/content/records.ts` exports `contentCommand(db, config, headers, command)` as a **server-only use case**, not a new HTTP endpoint or browser API. It reuses the local opt-in identity configuration and authenticated transaction lock, requires the configured Origin, a verified adult session with MFA no older than five minutes, and the existing local bootstrap operator identity. Ordinary guardians do not gain content-management permission. D14’s first bounded UI reuses only this bootstrap-operator authority; broader content-author roles remain future work. The internal `contentCommandInTransaction` composes commands within an already authorized, locked transaction; it does not authorize its caller. The original `contentCommand` wrapper retains its checks. See [D14 batch review](d14-batch-review.md) for the new local synthetic route and explicit review/publication controls.

Supported commands are `register-coverage`, `create-rubric`, `create-content`, `review` and `publish`. Inputs have exact key sets and a bounded JSON envelope. Create commands use caller-supplied UUID identities and positive revisions for safe retries; the service generates record IDs. Review/publication require the exact returned content hash. Review derives its actor from the authenticated session. Responses are no-store and mutations return only IDs/hashes/scope; errors do not log content, keys or session material.

Coverage registration occurs only on an explicit authorized command; no migration/startup seed publishes content. No operator/customer database was touched for this task: tests register the ledger in a disposable PostgreSQL instance and clean it up. No live content review has occurred. This is an implementation for the future authoring UI, not a claim that the UI is available today.

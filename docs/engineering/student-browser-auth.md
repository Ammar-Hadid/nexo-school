## Explicit local origin

Use the D02 synthetic database/bootstrap setup with **`BETTER_AUTH_URL=http://localhost:3000`** (or one explicitly selected local port). Open that exact origin for all guardian and student operations. PostgreSQL remains `127.0.0.1`; the configuration still rejects remote databases and non-synthetic names. The existing IP-based origin remains accepted for D02 adult operations, but all D04 routes fail closed there: WebAuthn rejects an IP address as a relying-party domain. Local passkeys use RP ID `localhost`; never derive origin/RP ID from forwarded headers.

Keep this origin and the auth secret stable across local restarts. Different ports are different origins, even though the RP ID remains localhost. Switching between localhost and the IP address does not transfer cookies. A future hosted origin needs its own reviewed HTTPS/host-only Secure-cookie configuration, enrollment and device testing; this local configuration cannot enable hosting. Local cookies are HttpOnly, SameSite=Strict, Path=/ with no Domain and intentionally lack Secure for loopback HTTP only.

## State and authority

`StudentBrowser` holds a SHA-256 hash of a random 256-bit browser cookie, a display label, enrollment expiry, grant expiry, selected student, approving guardian and credential association. The enrollment UUID is a lookup/confirmation identifier for the guardian; possession of it never supplies the browser secret or login authority. Browser labels are untrusted user descriptions, not fingerprints or attestation.

A browser requests an enrollment without supplying a student ID. The guardian selects a D03 profile and approves that enrollment with the active `manage` capability and MFA no older than five minutes; future-dated proof is rejected. Enrollment is valid for ten minutes. Approval is consumed once. Repeating the initial request with the same pending browser cookie returns its enrollment ID; duplicate approval returns 409. The local synthetic endpoint caps new enrollment records at 20 per minute globally, persisted in PostgreSQL; library challenge/verification endpoints retain D02's database rate limits. No forwarded IP bypass.

State transitions are `pending → approved → registering → active`, or revocation. Registration uses the library's supported pre-auth `resolveUser` and `afterVerification` hooks. Its server-side verified user-verification flag must be true. Client-supplied identities and `createSession` are rejected. Registration creates a credential and activates its grant, but creates **no student session**. The student subsequently proves the passkey to sign in. An independently approved browser may instead prove an existing synced student credential, activating that browser's grant on successful authentication.

The library does not require user verification by default in its verifier. Both D04 verification hooks enforce the verified flag; authentication options also request it. Challenge/signature/origin/RP/counter verification and credential persistence remain library-owned. See the [official passkey documentation](https://better-auth.com/docs/1.6/plugins/passkey) and installed source `node_modules/@better-auth/passkey/dist/index.mjs`; no spike runtime code is imported.

`StudentSessionBinding` associates each successful library student session with that browser grant and its last activity. Every protected request must use `withStudentIdentity` from `src/server/auth/service.ts`, which checks the real database session, student principal, active unexpired browser cookie, exact session binding, credential existence/ownership and the approving guardian's still-active management relationship. It rejects inactivity of 30 minutes or more and future activity timestamps. Sessions retain D02's 12-hour maximum and disabled cookie caching. The 90-day browser grant and other durations are local synthetic ADR-003 defaults, not a newly approved production duration policy.

The callback receives a trusted student actor and must still use D03's scoped resource policy for the requested resource. A raw Better Auth student session, a passkey alone, a browser cookie alone, or a session copied without its browser cookie never grants student access. Cookies can be stolen; this is browser authorization, not hardware attestation or biological identity proof.

Every mutation, library operation, audit write and binding write shares D02's PostgreSQL advisory transaction lock. Library server failures, post-verification write failures and audit/binding failures roll back. Expected verification denials retain the library's attempt/challenge handling. A lost successful response may leave a valid registered key or a bound session on the server, but cannot expose an unbound session. The same assertion can retry after a rolled-back transaction; a committed assertion is single-use. This is bounded local serialization, not a throughput claim.

## HTTP surface

All routes below are under `/api/auth`. These are operator/test surfaces, **not reviewed authentication screens**. Responses are `no-store`; authority/secret hashes/public keys and library session tokens are never returned as student JSON. POST bodies retain the 8 KiB limit and exact configured Origin requirement. D04 GET requests require the exact Origin or browser `Sec-Fetch-Site: same-origin` when Origin is absent. Unexpected fields and query parameters are rejected, apart from the registration `context` parameter.

| Method/path                                        | Contract                                                                                                                                                              |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| POST `/student/enroll`                             | Exactly `{label}`. Sets the opaque browser cookie; returns `{enrollmentId,label}`. Display/compare the ID and label on the guardian's separate authenticated browser. |
| POST `/student/approve`                            | Exactly `{studentId,enrollmentId}`. Fresh guardian MFA and management capability; approval/audit atomic.                                                              |
| POST `/student/browsers`                           | Exactly `{studentId}`. Fresh management MFA; returns only ID, label, state and expiry.                                                                                |
| GET `/passkey/generate-register-options?context=…` | Approved enrollment ID plus its browser cookie.                                                                                                                       |
| POST `/passkey/verify-registration`                | Exactly `{response}` from WebAuthn. Verified UV; registration only, no session.                                                                                       |
| GET `/passkey/generate-authenticate-options`       | Active grant or approved enrollment for an existing key.                                                                                                              |
| POST `/passkey/verify-authentication`              | Exactly `{response}`. Verified UV, matching student/key/browser; session and binding commit together. Returns only `{ok:true}` and library HttpOnly cookies.          |
| GET `/student/session`                             | Fully revalidated session; returns only `{student:{id,displayName}}`.                                                                                                 |
| POST `/student/revoke`                             | `{studentId,scope:"browser"                                                                                                                                           | "credential",browserId}`or`{studentId,scope:"all"}`. Fresh management MFA; revokes affected grants/sessions atomically, deleting credentials for credential/all scope. |
| POST `/sign-out`                                   | Existing D02 route now also permits student logout.                                                                                                                   |

Generic passkey list/update/delete and other unlisted library routes remain denied. Enrollment completion/authentication refuses an existing authenticated session: sign out first when changing identity or unlocking after inactivity. This prevents an adult session from determining the registration principal; a shared browser must sign out the adult before student authentication. Sign-out invalidates the database session. A later reviewed UI must also clear its adult client state.

Recovery means a guardian revokes the lost browser/credential/all access as appropriate, approves a fresh enrollment and the student registers/proves a key. It preserves the D03 student ID and future learning records. Revoking only one browser leaves another approved browser usable; revoking a synced credential affects every browser using it. The server records secret-free audit events. Production notifications and adult loss-of-all-factors recovery remain separate release work.

## Verification and handoff

The integration suite uses a disposable local PostgreSQL database and real Chromium/CDP virtual authenticators, through a loopback HTTP adapter to the real identity handler. It does not mock signature verification. Shared D02 test helpers were extracted without changing D02/D03 test scenarios. The five D04 scenarios cover:

- Enrollment, independent login, minimal DTOs, no pre-login access, denied adult access, synced credentials on unapproved browsers, session cookies without the browser grant, second-browser approval, browser-only and credential-wide revocation, recovery preserving profile identity, and concurrent login/revoke-all.
- Signed registration/authentication without UV, committed assertion replay, idle lock and an otherwise valid library session lacking a binding.
- Concurrent duplicate approval, mismatched/missing browser cookie, expired enrollment, revoked supervision and stale MFA.
- Generic passkey endpoint denial, forged enrollment ownership, wrong HTTP origin, cross-family management denial, missing management capability, future MFA, repeat enrollment and persistent enrollment throttling.
- Database-injected audit failure after credential/session writes, rollback of credential/grant/session/binding state, and successful safe retry of the same assertion after rollback.

Executed on Node 24.22.0: `npm run test:identity` **29 passed** (24 existing D02/D03 + 5 D04); fresh migration plus replay passed and disposable containers were removed. `npm test` **124 passed in 24 files**; typecheck, zero-warning lint, Prisma validation and standalone production build passed. `npm run test:e2e -- tests/e2e/local-identity.spec.ts` **8 passed**, including three D04 routes denied without synthetic opt-in. Root formatting, local documentation targets across five touched documents and Git whitespace checks passed. No disposable identity test container remained. This is targeted verification, not an aggregate `npm run check` claim.

Initial failing browser runs exposed the IP-based RP incompatibility and the need to allow normal same-origin GET requests without an Origin header; both were corrected. The negative-UV test needed a CDP response override and restoration of the required-UV prompt before its positive login. A concurrent Prisma generation attempt caused an EEXIST/type-export build failure; sequential regeneration, typecheck and build then passed. No failed run is counted as passing. No physical device/Safari, hosted origin, VPS migration, remote CI, full Storybook/learner E2E/visual suite or new auth-screen review is claimed. The accepted spike evidence remains unchanged. D03 and D04 migrations are local only. No real learner data, live AI, public deployment or new content/educational approval.

## Research findings and implementation implications

**Reuse Better Auth and the current mechanisms.** Better Auth documents credential sign-in followed by a distinct second-factor challenge; password success alone is not completed MFA sign-in. Keep the current guardian password/TOTP mechanism and student passkeys. Adding social login, public registration, a second identity service or a weak student PIN is unnecessary for this private application. This recommendation follows the existing [ADR-003](../architecture/decisions.md#adr-003--guardian-approved-enrollment-independent-passkey-login), not a new method selection. [Better Auth 2FA](https://better-auth.com/docs/plugins/2fa).

**Five-minute freshness is separate from being signed out.** The current adult identity adapter accepts a valid MFA-authenticated session; content management additionally requires recent proof, including authoring GET reads such as the delivery overview, not only mutations. `service.ts` updates `mfaVerifiedAt` after successful `/two-factor/verify-totp`. The installed Better Auth 1.7.10 `verifyTwoFactor` implementation accepts an existing session, and its TOTP endpoint verifies that session's user's factor. Therefore an in-place TOTP re-verification flow appears supported; restarting a rehearsal is not a fundamental authentication requirement. This is source inspection, not a newly executed regression test. Test the complete stale-proof → verify → retry-original-action path before claiming it delivered. Preserve current freshness requirements; do not silently extend durations or enable `trustDevice`, which the wrapper currently rejects. Installed-source evidence: `node_modules/better-auth/dist/plugins/two-factor/{verify-two-factor.mjs,totp/index.mjs}` and `src/server/content/delivery.ts`.

OWASP recommends reauthentication for sensitive operations while minimizing unnecessary disruption. This supports a clear in-app verification step; it does not establish a particular five-minute duration or justify relaxing the existing policy. [OWASP authentication guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#reauthentication-after-risk-events).

**Hide authenticated UI when signed out, while preserving server enforcement.** Next.js recommends authorization near protected data and warns that layouts alone may not recheck sessions on every navigation. The new entry composition should use the same authoritative identity/capability boundary as the APIs, clear protected client state on denial/logout, and distinguish loading, signed out, wrong role/permission, expired recent proof and service failure. A 401, a 403 for access or stale MFA, and a disabled/unavailable service must not become the same generic sign-in message; do not assume every 403 means a TOTP prompt is appropriate. No hardcoded person name should imply an authenticated session. UI gating supplements existing API checks. [Next.js authentication guidance](https://nextjs.org/docs/app/guides/authentication).

**Give the manual environment a stable identity.** Better Auth explicitly supports `localhost` as RP ID and configured localhost origins for local WebAuthn. Keep the hostname, configured port, auth secret and synthetic database stable across ordinary restarts; separate an explicit reset from stop/start. Use two normal browser profiles for simultaneous guardian/student testing, because tabs in one profile share the session cookies; a role selector is not authentication. [Better Auth passkeys](https://better-auth.com/docs/plugins/passkey).

Localhost credentials should not be presented as credentials already qualified for a later hosted domain. WebAuthn scopes credentials to a relying party and verifies the ceremony's origin. Testing on the Samsung tablet requires a suitably configured accessible secure origin and separate environment authorization; a Mac's localhost URL is not a tablet environment. Preserve the accepted earlier device spike evidence without claiming it qualifies this new main-app integration. [WebAuthn specification](https://www.w3.org/TR/webauthn-3/), [Secure Contexts](https://www.w3.org/TR/secure-contexts/#is-origin-trustworthy).

## Proposed bounded deliverable

1. A documented one-time local synthetic owner setup using the existing bootstrap/outbox mechanisms; no default credentials or public signup. Subsequent use must start from ordinary signed-out browser windows and no hidden session injection.
2. Guardian sign-in with password, TOTP, existing backup-code recovery and clear sign-out. Give missing/expired proof a direct recovery route. Basic recovery must be usable; real email delivery and hosted loss-of-all-factors operations remain environment work.
3. Student request/approve/register flow using existing browser grants and passkeys; then independent daily login. Expose guardian revocation/re-enrollment without changing student identity or learning records.
4. Shared route/session presentation across guardian content and results and student task pages, preserving approved layouts. Return to a validated internal destination after login or recent-proof verification; never accept arbitrary external return URLs.
5. Stable local synthetic persistence plus explicit start/stop/reset instructions. The user can close both browsers, restart the app and return to the same accounts and saved work.

Acceptance should include wrong credentials/code, interrupted enrollment, wrong-role and unauthenticated direct links, sign-out/back navigation, expired/revoked sessions, stale-MFA re-verification, independent student re-login, browser/app restart and saved content-to-result review. Use real local PostgreSQL and actual library ceremonies. Existing virtual-authenticator tests remain regression coverage; a human browser walkthrough establishes the manual handoff. New screens/notices require their normal design review, while prior approved presentation remains reused.

Do not add the full daily planner, curriculum, progression, Gamepas, public hosting or production-email integration to this slice. A local authentication experience is timely; a claim of production readiness is not. The 210 requirements, daily Redactiesommen, 15–30-minute review target and €10/month ceiling are unchanged.
